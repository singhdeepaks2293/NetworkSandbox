# MASTER DEVELOPMENT PROMPT: Upgrade NetworkSandbox into a Production-Oriented Docker NGFW

## PROJECT

Repository: https://github.com/singhdeepaks2293/NetworkSandbox

Project directory: `firewall/`

Objective: Transform the existing Rust-based Docker firewall into a feature-rich, secure, enterprise-style Next-Generation Firewall (NGFW).

This is an upgrade of an existing project, NOT a greenfield rewrite.

The existing firewall already includes:
- Rust-based IPv4 packet forwarding.
- Stateful session tracking.
- Firewall policies and zones.
- SNAT, DNAT and PAT.
- Basic HTTP/TLS metadata inspection.
- Basic IPS and antivirus signature matching.
- DoS thresholds.
- REST API.
- Web management interface.
- Basic CLI.
- Candidate/running configuration.
- Commit, rollback and audit functionality.
- Docker and containerlab integration tests.

Preserve these working capabilities wherever practical.

---

# ABSOLUTE DEVELOPMENT RULES

1. Inspect the complete existing repository before changing code.
2. Understand the existing architecture and identify reusable modules.
3. Do not delete working features simply to simplify implementation.
4. Do not replace real functionality with mock data, simulated responses or decorative UI.
5. Do not claim a feature is implemented unless its backend and integration tests prove it.
6. Every API endpoint must perform its advertised operation.
7. Every UI button must perform a real action.
8. Every CLI command must execute real backend functionality.
9. UI, CLI and REST API must use the same configuration and policy engine.
10. Maintain backward compatibility with existing configuration wherever practical.
11. Avoid unnecessary dependencies and excessive memory usage.
12. Never silently ignore unsupported configuration.
13. Use secure defaults.
14. Do not introduce hardcoded credentials, API keys or passwords.
15. Do not disable security checks to make tests pass.
16. Never run destructive commands against the host system.
17. Never use Docker privileged mode as the default deployment requirement.
18. Do not report successful tests unless they were actually executed.
19. Document incomplete functionality explicitly.
20. Work phase by phase, committing stable changes and keeping the repository buildable.

Target architecture:
- Rust backend.
- Linux packet enforcement.
- Docker-first deployment.
- Modern enterprise firewall web interface.
- Interactive network-engineer CLI.
- REST API.
- Shared policy/configuration engine.

Support lightweight and full NGFW profiles.

# PHASE 2 — KERNEL-LEVEL FIREWALL FOUNDATION

The goal is to evolve the existing userspace packet-forwarding architecture into a reliable Linux kernel-integrated firewall.

Do not abruptly remove the existing forwarding engine.

Implement kernel integration incrementally with compatibility and rollback.

## 2.1 nftables integration

Implement a dedicated Rust nftables backend.

Requirements:
- Create and manage nftables tables.
- Create input, output and forward chains.
- Configure firewall rules.
- Configure zone-based filtering.
- Configure source NAT.
- Configure destination NAT.
- Configure masquerading.
- Configure port forwarding.
- Configure connection-state rules.
- Support IPv4 and IPv6.
- Support rule counters.
- Support logging.
- Support default-deny policies.
- Support atomic ruleset updates where possible.

Never flush or overwrite unrelated host firewall rules.

Use a dedicated table and clearly documented ownership boundaries.

## 2.2 Linux conntrack

Integrate Linux connection tracking.

Requirements:
- NEW.
- ESTABLISHED.
- RELATED.
- INVALID.
- TCP connection tracking.
- UDP flow tracking.
- ICMP tracking.
- Session expiration.
- Connection counters.
- NAT state tracking.
- Session monitoring API.

Avoid maintaining duplicate connection state unless there is a clearly justified reason.

## 2.3 NFQUEUE integration

Implement selective NFQUEUE inspection.

Requirements:
- Queue selected traffic based on firewall policy.
- Avoid sending every packet to userspace unnecessarily.
- Support packet verdicts:
  - ACCEPT
  - DROP
  - REPEAT, where supported and safe.
- Configure queue numbers.
- Configure queue lengths.
- Configure fail-open/fail-closed behavior explicitly.
- Handle queue overload.
- Handle inspection timeouts.
- Provide queue statistics.
- Prevent packet-processing deadlocks.
- Ensure packets are not accidentally processed twice.

Support policy-based inspection.

Example:

- Ordinary trusted traffic: kernel fast path.
- DNS traffic: DNS inspection.
- HTTP traffic: HTTP inspection.
- Selected TLS traffic: TLS metadata inspection.
- Suspicious traffic: deeper inspection.

## 2.4 IPv6

Implement complete IPv6 firewall support.

Include:
- IPv6 packet parsing.
- IPv6 addresses and objects.
- IPv6 zones.
- IPv6 firewall rules.
- IPv6 stateful filtering.
- ICMPv6.
- Neighbor Discovery.
- IPv6 extension-header handling.
- IPv6 NAT only where explicitly supported and appropriate.
- IPv6 logging and monitoring.

Do not treat IPv6 as an optional checkbox while allowing it to bypass firewall policy.

## 2.5 Interface and routing management

Implement:
- Interface discovery.
- Interface status.
- Interface configuration.
- IP address configuration.
- VLAN support.
- Routes.
- Default gateways.
- Static routes.
- Interface counters.
- Link status.
- MTU.
- DNS configuration.

Any host networking modification must be validated and reversible.

## 2.6 Optional eBPF/XDP acceleration

Design an optional acceleration module.

Use eBPF/XDP only where it provides a measurable benefit.

Requirements:
- Basic packet filtering.
- Flow classification.
- Counters.
- Drop statistics.
- Safe program loading.
- Verifier-compatible programs.
- Fallback when unsupported.
- Clear capability detection.

Do not make eBPF mandatory for basic firewall functionality.

## PHASE 2 DEFINITION OF DONE

- nftables integration works on Linux.
- Kernel connection tracking is integrated.
- NFQUEUE selective inspection works.
- IPv4 and IPv6 policy enforcement works.
- NAT works.
- Existing host rules remain protected.

## DEVELOPMENT EXECUTION STRATEGY

Do not attempt to implement all five phases in one uncontrolled code-generation operation.

Work in this order:

1. Inspect the repository and produce an architecture assessment.
2. Create an implementation plan with actual file paths.
3. Implement Phase 1.
4. Build and test Phase 1.
5. Fix all regressions.
6. Implement Phase 2.
7. Build and test Phase 2.
8. Continue through Phases 3, 4 and 5.
9. Run complete regression tests.
10. Update documentation and implementation status.

After each phase, provide:

- Files created.
- Files modified.
- Features implemented.
- Features still incomplete.
- Security improvements.
- Test results.
- Build results.
- Known limitations.
- Commands to run the project.

Do not stop after producing a plan or UI mockup. Continue implementing until the requested phase is genuinely complete, subject to available tools and environment.
